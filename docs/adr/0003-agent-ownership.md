# ADR-0003 · Agent 归属：绑上下文，不绑人也不绑平台

- 状态：已接受
- 日期：2026-08-12
- 影响面：预演、群聊介入、扩展性、成本模型

## 背景

「智能体到底是每个人一个，还是平台上有一个专门管分发的？」——
两种直觉都有问题：每人一个常驻 agent 在千人规模就是千个进程加状态同步噩梦；
平台单一 agent 又会变成一个什么都管的黑箱。

## 决策

**按上下文绑定，共两个角色；平台不设 agent。**

| 角色 | 绑定 | 状态 | 记忆来源 |
|---|---|---|---|
| 代理人 Agent（Proxy） | `person` | **无状态** | 该用户的可披露切面（每次从 DB 读） |
| 池塘精灵（Spirit） | `pool` | 有状态 | 该池塘的 `episode` 与 `artifact` |

### 代理人 Agent 是函数，不是进程

它不是「每个用户有一个常驻的 AI 助手」，而是「带着你的可披露切面执行一次任务」
的函数调用。所有状态都在数据库里（`facet` / `relation` / `intent`），
agent 本身不持有任何东西。

这个区分决定了扩展性：**1000 个用户不等于 1000 个进程**。
也决定了正确性：不存在「你的 agent 记得的」和「数据库里的」不一致的可能。

### 池塘精灵才有状态，因为它的记忆本就属于池塘

「我们上次爬山迷路了」这条记忆不属于任何一个人，它属于那次爬山。
挂在个人身上会导致双方记忆不一致、无法共同编辑、无法作为共同资产展示。

`kind='dyad'` 的池塘退化后，它的精灵恰好就是抖音小火人 —— 本模型是它的严格超集。

### 平台不设 agent

分发不是 agent 问题。分发是 SQL 硬过滤 + 向量检索 + 加权排序 ——
确定性、可解释、可测、便宜。用 agent 做分发会让这四样全部失去，
且成本高两个数量级。

唯一用到模型的是漏斗末段的终排与生成理由，那是**一次无状态调用**，
不是一个常驻的「分发智能体」。

## 后果

- 预演时双方的「代理人 Agent」是同一份代码、不同的输入（各自的可披露视图）。
  不需要为每个用户维护 agent 实例、prompt 或配置。
- 池塘精灵的记忆随池塘生命周期存续，池塘休眠它也休眠。
- 新增一类 agent 行为时，先问它属于哪个上下文；答不上来说明它其实是一段确定性逻辑。

## 拒绝的替代方案

**每人一个可自定义人格的常驻 agent。** 听起来更「AI 原生」，
但它引入了状态同步、人格漂移、以及「我的 agent 说过什么我不知道」的信任问题。
而本产品的立场是 AI 只做预演、真人签字 —— 一个有自己人格和记忆的代理人
会不断诱惑我们放松那条红线。
