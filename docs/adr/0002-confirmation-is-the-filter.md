# ADR-0002 · 确认即过滤：不做时间窗与严格准入

- 状态：已接受
- 日期：2026-08-12
- 影响面：意图槽位、匹配漏斗硬过滤段、提案卡、池塘成员生命周期

## 背景

初稿把意图里的时间建模成结构化区间 `{start, end}`，并在匹配漏斗第一段
做「时间窗重叠」的 SQL 硬过滤；槽位还区分 `hard`（不可让步，走硬过滤）
与 `soft`（可商量，走向量与重排）。

## 决策

**取消时间窗与基于它的硬过滤。时间退化为自由文本，只作为语义信号参与排序与展示。**

匹配漏斗的硬过滤只保留物理约束：同校区、未拉黑、未过期、非本人。

**准入由人完成：发布组队或收到邀请，确认加入即可；不确认就是不合适，
系统不需要知道原因。** 确认之后仍可退出 —— 成员表本就有 `left_at`。

## 依据

**它解决的问题不存在。** 「确认加入」这个动作本身就是过滤器。时间不合适的人不会点确认，
系统不需要替他判断。而且确认之后聊下来发现不合适再退出，本来就是正常的社交流程 ——
在匹配阶段假装能算准，是把一个流动的过程钉成静态约束。

**它带来的机制远比它省下的麻烦多。** 「周末」「下周有空的时候」「考完试」
这类真实表述无法可靠地落成区间；时区、周期、模糊边界每一项都是坑。
而误判的代价是不对称的：把本来合适的人直接筛掉，**用户永远看不到，也无从申诉**。
宁可多推几个不合适的让人自己划掉，也不要少推一个合适的。

**它与产品的基本立场一致。** 四条人类决策权里的第一条就是「连接对象由真人决定」。
用时间窗替用户预先筛人，是把决策权悄悄拿回系统手里。

## 后果

- `IntentSlots.when` / `size` 改为自由文本，不做区间或数值解析。
- 删除 `IntentExtraction` 的 `hard` / `soft` 槽位数组，以及 `intent` 表的
  `hard_slots` / `soft_slots` 列。
- `ProposalCard.actionProposal` 的 `when` 是给人看的起点（「这周六上午」），
  不是给系统算的约束；具体几点由参与者自己聊定。
- 决策卡的时间选项是文本提示（`whenHint`），不参与任何计算。
- 意图的 `expires_at` 保留 —— 它约束的是意图在广场上的存活时间，
  不是「活动必须在此之前发生」。后者又会滑回时间窗那套机制。
- 匹配质量因此更依赖语义排序，这反过来提高了 embedding 与重排的重要性（见 ADR-0001）。

## 代价

会出现「两个人都想爬山但时间实际凑不上」的匹配。这是刻意接受的：
它的成本是一次没成的对话，而反面的成本是一个本可以成的连接从未发生。
