## 踩过的坑
================================================================

1. RLS 策略无限递归
   person 的策略里查 person、membership 的策略里查 membership，策略求值又触发策略。
   修法：把主体查询放进 SECURITY DEFINER 函数（current_person_id / current_campus_id /
   is_pool_member / person_campus / relation_temperature），并固定 search_path = public。
   新增涉及跨表判断的策略时，先想清楚会不会自引用。

2. RLS ≠ 可访问
   RLS 只决定哪些行可见，表级 GRANT 决定这张表能不能碰。缺 GRANT 时策略再对也是
   permission denied。按最小权限逐表授予，不要 grant all on all tables ——
   那样将来新增的敏感表会被静默放开。

3. 后台命令被沙箱 SIGTERM
   run_in_background 的 brew / supabase start / create-next-app 会静默失败或被杀。
   长任务用 `nohup cmd > /tmp/x.log 2>&1 &` 脱离进程组。

4. supabase start 失败于孤儿容器
   被 kill 过的运行会留下 supabase_db_<project> 容器，再启动报名字冲突。
   先 `supabase stop --no-backup` 并 docker rm -f 残留容器。

5. 不要用「模型应该答错」来测重试路径
   模型看了 schema 会照对的答，测试反而挂。要验我们自己的抛错路径，
   用恒假的 zod refine —— 把断言建立在模型服从性上，测试就成了抽奖。
